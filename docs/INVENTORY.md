# Интерактивный выбор квартиры — архитектура и спецификация

Путь покупателя: **Проект → Корпус → Этаж → Квартира → Планировка → Стоимость → Заявка.**
Функция встроена в существующий сайт (Next 16 App Router, статический экспорт на GitHub Pages,
RU/RO, три темы, живая — Premium Dark). Визуальные правила — `docs/DESIGN-SYSTEM.md`.

---

## 1. Данные

```
src/lib/inventory/types.ts        доменная модель (ProjectInventory → Building → FloorPlate/Floor → Apartment)
src/lib/inventory/repository.ts   ЕДИНСТВЕННАЯ точка чтения данных (getInventory, stats, *Params…)
src/lib/inventory/plan-generator.ts  параметрические 2D-планы квартир из слота этажа
src/content/inventory/*.ts        данные проектов (сейчас — DEMO для botanic-star-2-blocks-3-4)
```

- Квартиры хранятся **плоским списком** (как таблица CRM/CMS): `id, number, projectSlug, buildingId,
  floor, slot, rooms, type, area, balconyArea, outdoor, bathrooms, pricePerSqm, totalPrice, status,
  plan2D, model3D, features`. Этажи и статистика вычисляются (`repository.stats`).
- **Подключение backend/CMS/CRM:** сохранить сигнатуры функций `repository.ts` и заменить их тела
  (fetch на этапе сборки для статического сайта; async + fetch на Node-хостинге). Компоненты не
  импортируют `src/content/inventory` напрямую.
- **Демо-данные:** `inventory.demo = true` → на каждой странице подбора видна плашка «Демо-данные»,
  страницы помечены `noindex`. Реальные данные: заменить модуль и поставить `demo: false`.
- Геометрия в метрах: площадка (`site`), пятна корпусов (`footprint`), типовые этажи (`plates` со
  `slots`), планы квартир (`plan2D.rooms[].polygon`). Эти же числа будут экструдироваться в 3D.
- Демо не выходит за опубликованные факты проекта (`src/content/projects.ts`): у Botanic Star 2
  «Типы квартир: 1–3 комнаты», поэтому широкие угловые квартиры и пентхаусы — большие 3-комнатные
  (у пентхауса отдельная кухня: гостиная + 2 спальни). Чипы комнатности, выбор комнат в
  калькуляторе (`roomCoefficients` в pricing.json) и подбор берут значения из данных — при смене
  фактов меняются данные и прайс, а не компоненты.

## 2. Цены — `src/config/pricing.json`

Владелец меняет цены без кода: базовая цена м² по проекту, коэффициенты корпуса / этажа (диапазоны) /
комнатности / типа квартиры, доля цены м² для балкона/террасы, цены парковки, параметры рассрочки
(сроки, мин/макс/по умолчанию взнос, годовая ставка; 0 = беспроцентная рассрочка застройщика).
Движок: `src/lib/pricing/engine.ts` (`pricePerSqm`, `estimate`, `installment`, `formatEUR`,
`formatArea`). Демо-квартиры посчитаны этим же движком — калькулятор и карточки не расходятся.
`pricing.demo = true` → рядом с ценами пометка «цены ориентировочные / демо».

- **Формат сумм:** `formatEUR` группирует разряды по локали: RU — пробелом (`€122 670`),
  RO (`ro-MD`) — точкой (`€64.700`), это норма румынского языка и так на всех RO-страницах.
  Поведение не менять: оба варианта верны для своего языка.
- **Калькулятор** (`src/components/inventory/calculator/`): `CostCalculator` — серверная обёртка
  (список проектов, диапазоны, контекст квартиры считаются на сервере) вокруг клиентского
  `CalculatorClient`; в браузер уходят несколько маленьких объектов, не весь инвентарь.
  Блок рисует свой заголовок, но **не рисует фон и отступы** — его ставят внутрь `<Section>`
  страницы; якорь `#calculator`, «Оставить заявку» ведёт на `#lead`. `preset.apartmentId`
  заполняет поля цифрами квартиры — оценка совпадает с её ценой.
- **Диапазоны калькулятора** (`src/lib/pricing/calculator.ts`): варианты комнат — ключи
  `roomCoefficients` проекта; ползунки площади, этажа, балкона/террасы расширяются по
  фактическому инвентарю. Границы по умолчанию (`DEFAULT_CALCULATOR_LIMITS`) переопределяются без
  кода необязательным блоком `"calculator"` в pricing.json той же формы, что `CalculatorLimits`
  (любая часть: `area` по комнатам, `outdoorArea`, `floors`, `areaStep`, `downPaymentStep`,
  `installmentPrice`). Это пределы интерфейса, не цены.

## 3. Маршруты (статически генерируются)

| Шаг | URL | Файл |
|---|---|---|
| Выбор корпуса | `/{locale}/projects/{slug}/select` | `src/app/[locale]/projects/[slug]/select/page.tsx` |
| Выбор этажа | `…/select/{building}` | `…/select/[building]/page.tsx` |
| План этажа | `…/select/{building}/{floor}` | `…/select/[building]/[floor]/page.tsx` |
| Квартира | `/{locale}/projects/{slug}/apartments/{id}` | `…/apartments/[apartment]/page.tsx` |

Хелперы: `routes.selector / building / floor / apartment` в `src/i18n/routing.ts`. RO использует
`/ro/proiecte/…` (middleware переписывает первый сегмент; подсегменты языконезависимы). Каждая
страница: `generateStaticParams` из `repository` (× locales), `dynamicParams = false`, `robots:
noindex` при demo. Состояние выбора живёт в URL — «назад», ссылки и аналитика работают сами.

## 4. Вьюеры 2D сейчас, 3D потом — `src/components/inventory/viewer/types.ts`

Каждый шаг рендерится через интерфейс пропсов: `ComplexViewProps` (корпуса), `BuildingViewProps`
(этажи), `FloorViewProps` (квартиры), `ApartmentViewProps` (комнаты). 2D-компоненты реализуют их
сейчас; сцена Three.js / React Three Fiber позже реализует **те же пропсы** и подключается через
`ViewerMode = '2d' | '3d'` (переключатель «2D | 3D» на странице квартиры уже есть, 3D — «скоро»).
Выбор всегда по id (корпус, номер этажа, id квартиры); `model3D.nodeId` в данных связывает узлы
GLTF с этими id.

- **Два состояния на шаг:** `active…` — подсветка (hover, фокус), временная; `selected…` /
  `pinned…` — нажатие (тап, клик, Enter), держится до следующего выбора. Touch без hover
  работает через второе: `ComplexViewProps.selectedBuildingId`,
  `ApartmentViewProps.pinnedRoomId` + `onSelectRoom`. 3D-сцена обязана поддержать оба, иначе
  тап на телефоне в 3D поведёт себя иначе, чем в 2D.
- **Что вне контракта:** каждый вьюер получает от своего шага ещё срез словаря и
  презентационные пропсы — `labels` (ComplexScheme2D, ApartmentPlan2D), `t` + `common`
  (Facade2D, FloorPlan2D), `className`, `maxHeight`, `orientation`. 3D-двойник монтируется тем же
  шагом и получает те же extras — aria-label зон без новых строк. В интерфейсы контрактов словари
  не входят: это контракт данных и выбора.
- **Ориентация плана квартиры** (`src/components/inventory/apartment/orientation.ts`, только на
  сервере): план всегда рисуется фасадом вверх (plan-generator.ts); направление севера, сторона
  торцевых окон угловой квартиры и вид из окон (двор / улица) выводятся из слота типового этажа
  (`slot.facade`, положение `slot.rect` на плите, `features`) — данные не дублируются. Южный слот
  = плита, повёрнутая на 180°: север вниз, торцы меняются местами.
- **Прорисовка плана** — CSS-keyframes в CSS-модуле (`apartment/plan.module.css`), а не JS: анимация
  идёт прямо из серверного HTML, `animation-fill-mode: both` держит начальный кадр (без вспышки
  готового плана). Стены (`pathLength="1"`, stroke-dashoffset, 1.1 s) → перегородки по комнатам
  (шаг 70 ms) → окна и вход → подписи. Глобальное правило `prefers-reduced-motion` гасит всё.

План подключения 3D:

1. `npm i three @react-three/fiber @react-three/drei`; компоненты в `src/components/inventory/viewer/3d/`,
   загружать через `next/dynamic({ ssr: false })` только при выборе режима 3D.
2. `ComplexScene3D` (вращение, выбор корпуса, подсветка этажей), `ApartmentScene3D` (вращение
   квартиры, комнаты, материалы, день/вечер) — те же пропсы, что у 2D.
3. Заполнить `model3D` у проекта/корпусов/квартир (glb + nodeId). Виртуальный тур — отдельный
   режим того же вьюера.

## 5. Подбор (Smart Recommendation) — `src/lib/recommend/`

Контракт `RecommendationProvider.recommend(criteria, pool, limit): Promise<Recommendation[]>`.
UI вызывает только `getRecommendationProvider()` с `recommendationPool(slug)` (доступные квартиры)
и рисует `Recommendation[]`; форма строит диапазоны из пула (`recommendationBounds`), поэтому не
предлагает того, чего нет в продаже.

**Локальный скоринг** (`local.ts`, чистые функции — тестируются и работают в браузере, при
сборке или на сервере):

```
score = 0.88 × (взвешенное среднее заданных критериев) + 0.12 × (взвешенное среднее бонусов)
критерии  бюджет 0.35 · комнаты 0.30 · мин. площадь 0.20 · этаж 0.15
бонусы    выгодная цена м² (ниже медианы сопоставимых) 0.50 · терраса/большой балкон 0.25 · угловая 0.25
```

Незаданный критерий («Любое») выпадает из среднего, а не считается совпадением, — процент всегда
описывает заданное. Жёсткие пределы: дороже бюджета более чем на 10 %, комнат ±2 и больше, площадь
меньше минимума более чем на 20 % — не предлагается; ниже 0.5 — шум; не более 2 квартир одной
планировки (корпус + слот). Каждая рекомендация несёт `reasons` и `tradeoffs` (ключи → чипы из
словаря) и `breakdown` по факторам. Веса и пределы — `DEFAULT_WEIGHTS` / `LIMITS`.

**Подключение AI/ML** (подробно — комментарий в `src/lib/recommend/index.ts`):

1. `src/lib/recommend/api.ts` — класс с тем же `RecommendationProvider`: POST критериев, `limit` и
   id квартир пула во внешний сервис (serverless-функция с ключом модели; на статическом экспорте
   ключ в браузер не отдаётся).
2. Ответ `[{ id, score, reasons, tradeoffs? }]` сопоставляется с пулом по id — неизвестные id
   отбрасываются, модель не может «придумать» квартиру; `reasons` — только ключи `MatchReason`.
3. Вернуть его из `getRecommendationProvider()` (например, при
   `NEXT_PUBLIC_RECOMMEND_PROVIDER=api`) с откатом на локальный скоринг при ошибке или таймауте.

## 6. Заявки, аналитика

- `LeadSection`/`LeadForm` принимают `apartment` (контекст «Квартира №34, Блок 3, этаж 7»): поле
  уходит в заявку (`/api/lead` → Telegram/CRM; на статическом экспорте — переход на «Спасибо»).
- Калькулятор → заявка (`src/lib/pricing/lead-calculation.ts`): «Оставить заявку» в калькуляторе
  публикует строку расчёта («Расчёт: Блок 3 · 2 комн. · 63,7 м² · … — итого €101 200») и ключевые
  цифры; LeadForm показывает её как контекст и отправляет вместе с заявкой (запасной путь —
  событие `pamir:lead-calculation` или поле комментария).
- `src/lib/analytics.ts` → `track(event, props)`; сейчас dataLayer/console. События: selector_view,
  building_select, floor_select, apartment_open, apartment_view_mode, plan_download,
  calculator_change, installment_change, recommend_submit, lead_open, lead_submit.
  Общие имена свойств: `project`, `building`, `floor`, `apartment` (id квартиры), `source` / `via`
  (откуда действие: scheme, list, plan, recommend, calculator, apartment_page…), `action`.
  Никаких персональных данных (имя, телефон) в аналитике — только что спросили, не кто.

## 8. Визуальный язык подбора

Премиальный архитектурный, не «дашборд»: крупная светлая типографика, hairlines, много воздуха,
токены темы (никаких hex), квадратные углы.

- **Статусы на схемах:** доступна — заливка `accent/15`, контур `accent`, hover `accent/35`;
  бронь — штриховка (SVG pattern) `ink/25` на `ink/5`; продана — `ink/5`, контур `line/15`,
  не кликабельна. Легенда рядом с каждой схемой.
- SVG в метрах (`viewBox`), линии `vector-effect: non-scaling-stroke`, подписи `.label`.
- Движение: схемы «прорисовываются» при появлении (stroke-dashoffset / fade 600–900 ms,
  `ease-premium`), корпуса поднимаются из основания; hover — 200–300 ms. `prefers-reduced-motion`
  — без анимаций. Никаких ярких/игровых эффектов.
- Каждая схема имеет доступную альтернативу — список (корпуса / этажи / квартиры) с теми же
  данными, клавиатура (Tab/Enter), `aria-label` с числами.
- **Фокус в SVG:** глобальное `:focus-visible { outline: 2px … }` (globals.css) объявлено после
  утилит Tailwind и перебивает `outline-none`; в SVG Chrome рисует этот outline в единицах
  `viewBox` (метрах). Зоны схем гасят его `focus-visible:[outline:none]` (специфичность выше) и
  рисуют свой контур `accent` — видимый фокус обязателен.
- **Каркас шага** (`SelectorShell`): крошки, заголовок, индикатор «01 Корпус — 02 Этаж —
  03 Квартира», демо-плашка. Сетка заголовка `minmax(0, 1fr)` до `lg` — ничто не расширяет
  страницу; на телефоне у индикатора подписан только текущий шаг (остальные — номера, названия
  остаются для скринридера). Будущие шаги — `text-muted` (AA), «ещё не пройдено» передают
  hairline-связка `line/20` и отсутствие цвета `ink`. Имена навигации — из словаря через
  `a11y={{ breadcrumbs, steps }}` (никаких английских aria-label).
  **Телефон (< md) открывается на схеме:** полная демо-плашка уходит под контент шага, а в строке
  eyebrow остаётся метка `DemoMark` «■ Демо-данные ↓» — ссылка на плашку (`#selector-demo`), без
  лишней высоты; вертикальный ритм плотнее. С `md` плашка — между заголовком и контентом, как
  раньше. Цель на 390 × 844: первая зона схемы не ниже y ≈ 600 (шаги 1 и 2 — ≈ 550 и ≈ 610–620);
  поэтому контент шага на телефоне не должен открываться высокой панелью — переключатель этажей
  шага 3 (≈ 85 px над планом, зона сейчас на y ≈ 730) на телефоне стоит перенести под план.
- **Крошки** (`Breadcrumbs`): на узком экране прокручиваются по горизонтали и открываются на
  текущей странице (`flex-row-reverse` — начало прокрутки справа, без JS); затухание по краю,
  за которым скрыты пункты. Мелкий текст не набирается акцентным цветом: у демо-плашки акцент —
  только рамка и квадратная метка.
- Touch: первый тап выбирает и показывает карточку с кнопкой действия; действие — второй тап
  по кнопке. Hover-карточки только на устройствах с hover.
- Цена — крупно (`text-display-md/lg`, `tabular`), «от €X» в списках.
