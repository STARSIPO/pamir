## 1. Ключевой вывод: фича со зданием — это данные, а не картинка

Заказчик просит «навёл на здание — видно, что занято, что свободно».

Оба референса (solomon.md и inamstro.md) используют один и тот же плагин **Image Map Pro**: SVG-полигоны поверх растрового плана этажа. Ни один из них не делает 3D. И, что важнее, **ни один не отвечает на вопрос «занято или свободно»** — у inamstro строка цены `.plan__rate` вообще пустой `<span>`, у solomon единственный признак доступности это случайный разброс прозрачности полигонов без легенды.

Значит, конкурировать нужно не рендерами, а данными.

**Решение: схематичный фасад, сгенерированный из данных (SVG).** Не 3D, не растровая подложка.

Почему это лучше, а не хуже:

- красит статусом 100% квартир и никогда не расходится с рендером, потому что рендера нет
- поддерживает легенду, фильтры, клавиатурную навигацию и диплинки — растровая карта полигонов не может
- работает **без единого ассета**, а в `public/` сейчас лежит только `favicon.svg`
- когда придут рендеры, добавляется опциональное поле `polygon` в ту же модель, и тот же компонент рисует полигоны поверх фасада. Геометрия — это поле данных, а не отдельная фича

**3D отклонено осознанно.** Выбрать одну квартиру из вращающейся массы сложнее, чем прочитать раскрашенный фасад. Любой серьёзный инструмент подбора — включая оба референса — сводится к плоской проекции, потому что она читаемая. Если модель когда-нибудь появится, 3D должно быть декорацией над схемой, а не заменой ей.

Плюс к делу: `three` + `@react-three/fiber` + `drei` — это 160–250 КБ gzip JS **до** самой модели, плюс GLTF на 3–15 МБ и троттлинг на среднем Android.

## 2. Настоящий блокер — не рендеры, а таблица

Это самое важное в плане, и первая версия исследования этого не увидела.

Сейчас репозиторий не знает **ни этажности, ни количества квартир** ни в одном здании:

- `src/content/projects.ts` — у двух строящихся проектов по три карточки-типа планировок, у остальных четырёх `floorplans: []`
- `PLACEHOLDERS.md` прямо помечает этажность и общее число квартир как неподтверждённые («Всего квартир: 10 выглядит неправильно»)

Нарисовать фасад 12×8 — значит **выдумать здание**. Это ровно то, что запрещает `PLACEHOLDERS.md`.

### Что нужно запросить у заказчика

Один файл, семь колонок:

| блок / scară | этаж | № кв. | комнат | общая м² | статус | цена |
|---|---|---|---|---|---|---|

Статус из фиксированного списка: `свободна` / `бронь` / `продана` / `уточняется`.
Цена — число или «по запросу».

И два вопроса письменно:

1. **Кто ведёт этот файл?** (имя, не отдел)
2. **Как часто он меняется?**

Ответ на второй определяет архитектуру. Если чаще, чем мы деплоим, — сразу закладываем подгрузку `/inventory.json` в рантайме поверх статически отрисованной геометрии, иначе доступность будет свежа настолько, насколько свежа последняя сборка.

## 3. Фазы

### Фаза 0 — то, что можно делать прямо сейчас (≈2 дня)

Не требует ни данных, ни ассетов, ни решений заказчика. Чинит то, чего покупатель уже касается.

`src/components/project/Floorplans.tsx` — сейчас худший компонент в репозитории по доступности:

- оверлей зума получает Esc, блокировку скролла, фокус-трап и навигацию next/prev
- починить числовую сортировку на строке 22
- «м²» на строке 84 захардкожен по-русски и уезжает румынским посетителям — вывести в словарь
- склонение комнат: сейчас `roomLabel` схлопывает всё от 3 комнат в `room3`, нет форм для 0 и 4+
- хеш-диплинк на планировку
- статус `unknown` через существующий `StatusBadge`

Плюс линт: убрать 15 неиспользуемых импортов, переписать два эффекта с `setState`.

### Фаза 1 — модель данных и схематичный фасад (4–5 дней)

**Модель.** Расширить `src/content/types.ts`:

```ts
export type UnitStatus = 'available' | 'reserved' | 'sold' | 'unknown';

export interface Unit {
  id: string;
  entrance: string;        // блок / scară — НЕ выводится из сетки
  floor: number;
  positionInFloor: number;
  rooms: number;
  areaTotal?: number;      // общая, с балконом — по ней сравнивают покупатели
  areaLiving?: number;
  orientation?: string;
  status: UnitStatus;
  price?: number;
  planTypeId?: string;     // FK на Floorplan.id — иначе связать карточку и хотспот не на чем
  polygon?: [number, number][];  // появится в Фазе 2
}
```

**Геометрия выводится группировкой юнитов по этажам, а не произведением «этажи × квартир на этаже».** Кишинёвские дома продаются по подъездам: два scări с разным числом квартир, коммерческий партер из 3 помещений под 8 жилыми, мансарда. Жёсткая сетка это не выражает.

Ширина ячейки пропорциональна `areaTotal` — трёшка визуально шире однушки. Фасад это транспонированная таблица остатков.

**Статус кодируется тоном И текстурой**, никогда только цветом: свободна — фирменный зелёный заливкой, бронь — штриховка 45° через `<pattern>`, продана — отдельный сплошной тон. **Не прозрачностью**: графит `42 44 47` на белом при alpha 0.35 даёт примерно `#A9AAAC` — это 2.3:1 и провал WCAG 2.2 1.4.11, требующего 3:1 для нетекстовой графики.

**Демо-режим.** Пока подписанной таблицы нет, фасад живёт на явно помеченном демо-маршруте («Демо-блок / Bloc demo»), исключённом из sitemap, robots и экспортной сборки. Публикуем только по факту получения данных.

**Правки роутинга.** `src/i18n/routing.ts:104-120` — `parsePathname` оставляет только локаль, ключ маршрута и slug, а `switchLocalePath` собирает URL из этих трёх частей. Любой `?unit=` или `#unit-…` теряется при переключении RU↔RO. Патчить обе функции и `LanguageSwitcher`.

Использовать **хеш, а не `useSearchParams`**: при `output: 'export'` query-параметры не имеют серверного смысла, а `useSearchParams` требует обёртки `<Suspense>`, иначе маршрут деоптимизируется на сборке.

**Доступность — таблица первична, SVG это улучшение.** Не ARIA-грид поверх SVG: семантика grid на SVG хрупко ведёт себя в скринридерах и съедает день оценки. Табличное представление тех же данных обслуживает одновременно скринридеры, отсутствие JS, поисковики, мобильные и печать. В SVG — обычные `<a href="#unit-…">` с осмысленными именами.

Тач-таргет: WCAG 2.2 2.5.8 требует ≥24×24 CSS px. Фасад на 96 квартир в колонке 343px даёт ячейки примерно 40×20 — по короткой стороне мимо. Нужен заявленный минимум и брейкпоинт, на котором таблица становится основным элементом управления.

### Фаза 2 — когда придут рендеры (2–3 дня кода + срок от архитектора)

- поле `polygon` активно: тот же компонент рисует полигоны поверх фасадного рендера, взаимодействия и доступность те же
- уровень «план этажа» как третья ступень детализации: комплекс → блок → этаж → квартира
- реальные 2D-планировки в боковую панель
- dev-only инструмент `/admin/hotspots` для разметки полигонов кликом, исключённый из экспорта
- статические маршруты на квартиру `[locale]/projects/[slug]/units/[unitId]` + JSON-LD `Apartment` / `RealEstateListing`

Маршруты на квартиру — **только когда есть настоящие площади и цены.** Сотни страниц с текстом «Уточняется» это тонкий дублирующийся контент и минус в выдаче.

### Фаза 3 — только если закажут художника (1–2 дня интеграции)

Изометрические разрезы **по типам квартир, а не по квартирам** — 5–10 статичных картинок, парой с плоским планом в панели. Разбор inamstro называет эту пару самой ценной идеей на сайте. Это работа со стоп-кадрами, не с realtime-моделью: ~90% воспринимаемой ценности 3D за долю стоимости.

## 4. Анимации: CSS-first, минус одна зависимость

Обе анимационные библиотеки на референсах простаивают: solomon грузит GSAP + ScrollTrigger + SplitText — живой аудит DOM нашёл **ноль** инстансов; inamstro грузит четыре библиотеки анимаций с нулём классов появления. Они заплатили байтами и не отгрузили ничего.

**GSAP не добавляем.** Он бесплатен с апреля 2025, так что дело не в цене: это ~40 КБ gzip императивного кода на рефах, который форсит `"use client"` на каждую секцию, вставляет `pin-spacer` и ломает раскладку Tailwind, требует `ScrollTrigger.refresh()` на каждой смене маршрута и на загрузке шрифта.

**framer-motion не переименовываем, а удаляем.** Проверено: единственный потребитель — `src/components/ui/Counter.tsx:4`, и тот импортирует только `useInView` и `useReducedMotion`. Ни одного `motion.*` компонента в репозитории нет, то есть DOM-рендерер и движок layout-проекции сейчас **не попадают в бандл**. Эти два хука — примерно пятнадцать строк `IntersectionObserver` + `matchMedia`, которые уже написаны в `Reveal.tsx`. Тултип пикера не нуждается в `AnimatePresence`: смонтированный узел с переключением `hidden` и переходом opacity/transform даёт то же самое за 0 КБ и надёжнее под статическим экспортом.

Отдельно: `layoutId` **не работает на SVG** — проекция считается по блочной модели HTML. Морфинг прямоугольника квартиры в шапку панели через `layoutId` физически не собирается так, как это было предложено. Кросс-фейд, либо позже зеркалить прямоугольник абсолютно позиционированным `div`.

### Слои

**L0 — чистый CSS.** Ховеры, подчёркивания, подъём карточек, сдвиг стрелки, масштаб картинки, липкие колонки, прорисовка волосяной линии. Отсюда примерно 70% ощущения дороговизны, и это стоит ноль байт и не требует клиентской границы.

**L1 — `Reveal.tsx` остаётся**, его контракт «по умолчанию видно, JS только добавляет скрытое стартовое состояние» строго лучше, чем `whileInView` (в комментарии самого файла зафиксировано, что `whileInView` был ненадёжен для видимых при монтировании элементов во время гидратации — под `output: 'export'` это хуже вдвойне, потому что всем отдаётся один HTML). Но починить две вещи:

- `will-change-[opacity,transform]` висит на постоянной обёртке на строке 74 и никогда не снимается — это 60 вечных композиторных слоёв. Ставить только в состоянии `hidden`, снимать на `transitionend`
- `getBoundingClientRect()` в эффекте — 60 принудительных пересчётов раскладки во время гидратации. Брать первый entry из `IntersectionObserver`

Попутно: утверждение «в кодовой базе анимируется только transform» **неверно** — `Reveal` анимирует opacity от 0 на всех 60 местах использования. Инвариант transform-only относится только к keyframe `fade-up`.

**L2 — нативные scroll-driven анимации** (`animation-timeline: view()`) под `@supports`, фолбэк — финальное состояние. 0 КБ, работает вне главного потока, не требует клиентской границы. Firefox в 2026 всё ещё за флагом, поэтому только как прогрессивное улучшение, никогда как несущая конструкция. Писать руками в `globals.css` — в Tailwind 3.4 с `plugins: []` таких утилит нет. И каждый новый класс обязан попасть в блок `prefers-reduced-motion` в `globals.css:44-52`, где сейчас перечислены ровно два класса.

**L3 — view transitions: сначала проверить, потом планировать.** React 19.3 экспортирует `ViewTransition`, а **не** `unstable_ViewTransition` (проверено: `'ViewTransition' in require('react')` → `true`, `unstable_` → `false`). Флага `experimental.viewTransition` в схеме конфига next@16.3.4 **нет вообще** — поиск по `config-schema.js` и `config-shared.d.ts` пуст. Пока не установлено актуальное имя флага, фазу вокруг этого не планируем.

Когда дойдёт: `view-transition-name` должен стоять **только на активированной карточке** — N карточек с одним именем в документе заставляют браузер пропустить переход целиком. Плюс отдельное правило, потому что все три точки контроля reduced-motion слепы к анимациям уровня браузера:

```css
@media (prefers-reduced-motion: reduce) {
  ::view-transition-group(*),
  ::view-transition-old(*),
  ::view-transition-new(*) { animation: none !important; }
}
```

**L4 — Lenis откладываем.** Единственное, что добавляет байты, и самый рискованный пункт. Если когда-нибудь поедет — удаление `html { scroll-behavior: smooth }` обязано быть под `@media (pointer: fine)`, иначе якоря `#lead`, `#floorplans`, `#contacts` начнут прыгать у всех мобильных.

### Про LCP — исходная посылка была неверной

На главной **нет геройской картинки**. `Hero.tsx` рисует градиент, инлайновый SVG-силуэт города, `.grain` и размытый шар `blur-[120px]`. LCP на `/` — это заголовок h1, и transform-only `fade-up` его уже защищает.

Единственная настоящая геройская картинка — `ProjectHero.tsx:30`, и именно туда предлагалось поставить занавес `clip-path` на 1.1 с. Полностью обрезанный элемент не имеет видимой площади и не является кандидатом на LCP, пока не отрисуется, — занавес отодвинул бы LCP на длительность анимации на единственном маршруте с большой картинкой. **Занавес на LCP-элемент не ставим**, только на галерею и то, что ниже сгиба.

Реальный риск кадрового бюджета на `/` — параллакс под слоем `mix-blend-mode: overlay` и шаром с радиусом размытия 600px, а не JS.

### Что реально делает сайт застройщика дорогим

По убыванию воспринимаемого качества на килобайт:

1. Медленный масштаб картинки на ховере карточки (1.0 → 1.06 за 900 мс) внутри `overflow: hidden`, при неподвижном контейнере
2. Морфинг картинки проекта при переходе карточка → страница (когда разберёмся с view transitions)
3. Липкая шапка, сжимающаяся 88 → 72px с `backdrop-blur` — **уже реализована** в `Header.tsx`, заменить слушатель `scrollY` на сентинел `IntersectionObserver`
4. Заголовок, раскрывающийся по словам с шагом 40 мс
5. Закреплённая секция «процесс», где левая колонка `position: sticky` — нативно, без библиотек пиннинга
6. Волосяная линия фирменного зелёного, прорисовывающаяся слева направо под заголовком секции (`transform: scaleX()`)
7. Счётчики с `tabular-nums` — `.tabular` и `Counter.tsx` уже есть, добавить только `Intl.NumberFormat(locale)`

**Разбивку заголовков по словам делать на сервере,** не через SplitText. Сайт двуязычный: клиентская разбивка кириллицы и румынских диакритик (ș, ț, ă, î, â) рискует поломать графемы, вызывает reflow после подмены шрифта, а под `output: 'export'` второго шанса положить текст в HTML нет. Серверные `<span>` по словам + `animation-delay: calc(var(--i) * 40ms)`. По словам, никогда по символам.

## 6. Правила, которые план обязуется соблюдать

- **Палитра и текст не меняются.** `--brand: 124 193 43` и `--graphite: 42 44 47` — единственные определения в `globals.css:12` и `:17`. Три копии зелёного вне токенов (`Logo.tsx:22`, `Media.tsx:107`, `public/favicon.svg`) — это SVG `fill`, который не читает класс Tailwind; правятся синхронно, если токен когда-нибудь сдвинется.
- **Ни одна анимация не меняет раскладку.** Только `transform`, `opacity`, `clip-path`. Никогда `width`/`height`/`top`/`left`/`margin`.
- **Reduced motion — это финальное состояние немедленно, а не отсутствие контента.**
- **Каждая фаза заканчивается экспортной сборкой** `EXPORT=true NEXT_PUBLIC_STATIC=1 NEXT_PUBLIC_BASE_PATH=/pamir npm run build` и осмотром `out/`. Зелёный dev-сервер ничего не доказывает про GitHub Pages.
- **Ничего не выдумывать.** Ни этажности, ни площадей, ни числа квартир. Демо-данные — только на помеченном демо-маршруте вне индексации.
- **Бюджет первой загрузки JS: ≤120 КБ gzip**, из них на анимации ≤30 КБ. Проверка в CI, иначе бюджет не бюджет.
